# T-111: Same numbers on every machine

- **Role:** engine (arithmetic of caladrius-nca, -models, -fit, -engine), with a test-layer crate and developer tooling
- **State:** done
- **Depends on:** T-110
- **Source:** orchestrator brief, 2026-10-23, after a measurement on Linux (Rust 1.97, wasm32-unknown-unknown under Node 22): of 70,509 numbers returned by `Engine::execute` on 2 `nca.run` (Theoph), 30 `fit.run` (Indometh, 6 subjects x 5 weightings) and 18 command examples, 19,165 differed between the native build and the wasm32 build, by at most about 1e-8 relative, and the fit of Indometh subject 2 with 1/yhat weighting had a minimization trace of 6 entries natively and 5 in wasm. The cause is `f64::exp`, `ln`, `exp_m1`, `ln_1p`, `powf` and `powi`, whose precision the Rust documentation calls platform-dependent (wasm32-unknown-unknown already uses the `libm` crate's algorithms). Routing about 106 call sites through the pure Rust `libm` made the outputs identical there. Windows and macOS had never been measured, and the browser build is public.

## Goal

The desktop application, the command line, the MCP server and the page in the browser are one engine. What `Engine::execute` returns must not depend on where it runs, and a test must say so.

1. Reproduce first, with the tool of step 3, before any change: Windows native against wasm32 under Node.
2. Forward every platform-dependent float function reachable from a result to `libm`, ban the standard ones with `disallowed-methods` in `clippy.toml`, and look for other sources of non-determinism.
3. `cargo xtask digest`: a fixed workload through `Engine::execute`, one SHA-256 over the canonical JSON of the answers; the same workload in the wasm32 build under Node; a CI matrix that compares the digests.

## Decisions taken without asking (nobody could answer)

- **`libm` pinned `=0.2.16`** in the manifests of nca, models, fit, engine and xtask. A new version may round a function another way and would change every digest and perhaps the conformance table: upgrade on purpose. Its `exp`, `log`, `pow` are the FreeBSD/musl ports, below 1 ulp and not correctly rounded, with arch-specific code only for exactly rounded operations (`sqrt`, `scalbn`, `fabs`, `floor`...) and no `fma` in the functions used. The wasm32 digest did not move: that target has no system maths library and already ran a pure Rust port.
- **`powi` has no `libm` function** and its rounding depends on how the compiler lowers it (products when the exponent is known, a runtime call otherwise, the C runtime's `pow` on windows-msvc). It is written as the products it stands for: `sq` and `powi` in `caladrius-fit/src/arith.rs` (bit for bit the products of LLVM's expansion and of compiler-rt's `__powidf2`: the reviewer compared them on 3.02 million cases, including `i32::MIN` and `i32::MAX`, zero, plus and minus one and two, NaN, infinities and subnormal numbers). In the engine's SVG ticks, `pow10` reads the text `1e{k}` with the standard parser (the double nearest to 10^k for any k): `libm::pow(10, -5)` is one bit away from 1e-5, and a loop of products ran 2^31 times (1.6 s) on a span of one subnormal number (found in review, test added).
- **The ban is workspace-wide** (root `clippy.toml`, f64 and f32: exp, exp2, exp_m1, ln, ln_1p, log, log2, log10, powf, powi, sin, cos, tan, sin_cos, asin, acos, atan, atan2, sinh, cosh, tanh, asinh, acosh, atanh, cbrt, hypot, to_degrees, to_radians), because clippy takes the nearest `clippy.toml`. Opt-outs, in the crate root with the reason: `caladrius-ui` (axes, ticks, colours and the display of numbers; reviewed: nothing reaches a command parameter, a saved project, an export or the clipboard) and `caladrius-testkit` (the independent reference arithmetic the engine is checked against; plus a line in its five integration tests). The tests of the numerical crates call `libm` too, so they need no opt-out. The three sites of `xtask` (conformance formula checks) call `libm` as well.
- **A crate for the digest**, `caladrius-digest` (test layer): no file access and no clock, so it compiles to wasm32; `xtask` depends on it. The wasm module is built with `cargo rustc --lib --crate-type cdylib --profile web` (the profile of the page), so natively the crate stays an rlib. Its SHA-256 is written in the crate (FIPS 180-4 vectors tested): no new dependency.
- **The workload** (761 steps in 518 sessions, 92 of them answered by an error on purpose) is built natively from the oracle and the engine's own examples, and the same bytes go to both sides: the 24 command examples as one script, the 20 NCA cases (`nca.run`, 40 steps), the 30 fit cases (six data sets, Theoph, Indometh, infusion, zero order, lag and spec, under the 5 weightings; one `data.import` then one `fit.run` per subject, 215 steps), 374 `model.simulate` cases (one-compartment, two-compartment, multiple dosing), 92 refusals of the two-compartment and multiple-dose models, and one session of 16 steps, the plots of a Theoph fit (`plot.xy`, `export.plot`). The canonical text has sorted keys and the shortest text that reads back as the same double, so the last bit is in the digest. `--dump` keeps the text and `--diff` says which numbers differ and by how much.
- **CI**: `digest` matrix (ubuntu, windows, macos natively in release; ubuntu with wasm-bindgen 0.2.129 and Node 22 for wasm32), `digest-compare` fails on any difference and prints the report of `--diff`.

## Known gaps (listed, not fixed)

- `min`, `max` and `clamp` may return either zero when they meet +0 and -0 (the Rust 1.99 documentation says so): only the sign of a zero can differ between CPUs. The reviewer reproduced it with a CSV of concentrations -0, 0, -0: `reduce(f64::max)` in `caladrius-nca/src/observed.rs` (line 21) gives a Cmax of -0.0 on x86, where the AArch64 instruction `fmaxnm` returns +0.0 (read from its definition, not run here). The workload has no negative zero, so the digest cannot see it. It predates this card.
- `usize` is 32 bits on wasm32: an option above 4,294,967,295 (`max_iterations`, `n_curve`, `min_points`) is refused with another message there.
- Checked and clean: no `f32` outside the UI, no `mul_add`, no thread or parallel reduction, no clock in the engine, `HashMap`/`HashSet` only for lookups (results are built in insertion order), float formatting and parsing are the standard library's own.
- Measured here: x86_64 Windows (dev and release builds) and wasm32 under Node 22. Linux x86_64 and macOS (an arm64 runner, the one architecture where `fmaxnm` and friends could differ) only by the CI job.
