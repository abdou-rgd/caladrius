# T-112: A seal on every result, and the replay of a saved project

- **Role:** engine (`caladrius-engine`: the seal and `project.replay`), with the desktop application, the browser page, the command line, the MCP server and the digest
- **State:** done
- **Depends on:** T-111
- **Source:** orchestrator brief, 2026-10-23, after T-111. The engine now returns the same bits everywhere, but nothing in a result or in a saved project said so: an export carried no engine version and no hash of its input, and the history of a project (`caladrius-engine/src/history.rs`) had no version, no time and no seal, so nobody could open a saved project somewhere else and check that it reproduces bit for bit, which the README promises ("every number is re-derivable from a pinned version"). First audience: the pharmacometrics team of the demo of 2026-11-17.

## Goal

Anyone can open a saved project, in the browser page too, and check that it reproduces bit for bit.

1. A seal on every result: the SHA-256 of the command, its parameters and its answer, with the engine version, the git commit and the hash of the input data next to it, in each entry of the history and in the files a program writes.
2. In the MCP server the seal is in `_meta` only: Apothicaire's number gate must see no new digits.
3. `project.replay`: the history of a saved project run again from an empty project, step by step, with the first divergence; as an engine command, in the CLI and over MCP.
4. "Verify a project" in the desktop application and in the web page.
5. The replay in the `cargo xtask digest` workload, so that the CI matrix proves the seals identical on the four targets.
6. `docs/reproducibility.md` in plain words; the README changed only where a sentence becomes true; `docs/conformance.md` byte for byte unchanged.

## Decisions taken without asking (nobody could answer)

- **What is hashed.** The SHA-256 of the canonical text `{"command":..,"format":"caladrius-seal-1","outcome":{"ok":true,"result":..} or {"error":<code>,"ok":false},"params":..}`: keys in byte order, no space, each number as the shortest text that reads back as the same double (so the last bit is in the hash, and -0 is not 0). A failure is sealed by its error code, not its message, so a message can be reworded without changing a seal. The parameters are the ones received, not the ones with defaults filled in. The text is `crates/caladrius-engine/src/seal/mod.rs`; a change of what is hashed changes every seal and is a new `FORMAT` (a seal of another format is not recomputed; AGENTS.md rule 10 says so).
- **What sits next to the seal, not in it** (a later version that computes the same bits must give the same hash): the version of the engine, the git commit (`build.rs`, `CALADRIUS_GIT_COMMIT`, when the build knew it), `input` and the time. `input` is the SHA-256 of the CSV text for `data.preview` and `data.import`, else of the canonical text of the list of worksheets the parameters refer to (`worksheet`, or the worksheet of the `analysis`, `fit`, `a` or `b` they name, and for a plot of a fit the one its source reads), taken before the command runs. The time (`at`, RFC 3339 UTC) comes from a clock the front end gives (`Engine::set_clock`: the system time for the desktop, the CLI and the MCP server, `Date.now()` in the page); the engine reads none, so it still compiles to wasm32. The engine of the digest has no clock and no provenance (`set_provenance(false)`): a commit that computes the same bits gives the same digest.
- **Not sealed:** `project.load` (the file it opens carries its own seals, and its outcome depends on whether the session already had a history) and `project.replay` (it is the check). A refusal before any command ran (text that is not JSON, bytes that are not UTF-8) is recorded without a seal. The answers that echo the history (`project.save`, `history.list`) are hashed without the `at` and the `engine` and `commit` of the entries they list, which are not deterministic.
- **SHA-256 and the canonical JSON moved** from `caladrius-digest` into `caladrius-engine::seal` (the engine cannot depend on the test layer; the digest crate re-exports them). The SHA-256 is still our own (FIPS 180-4 vectors tested): no new dependency.
- **The commands return clean results; the programs that write a file add the stamp.** A seal cannot sit inside the text it seals. A CSV from the CLI starts with the line `# caladrius engine=.. commit=.. command=.. seal=.. input=..` (`data.import` and `data.preview` skip it, so an exported table can be imported again; other programs need `comment="#"`; `--no-seal` prints the answer as it is), an SVG saved by the application carries the same line as an XML comment after the root tag, and a JSON answer of the CLI has a `seal` member. A stamp holds no time: the same command on the same data gives the same file byte for byte.
- **The history** keeps the parameters of a command up to 64 KiB (unchanged), else `{omitted, bytes, digest}` with an FNV-1a 64 digest; an entry gets `seal` and `at`; a file without them loads (every step then replays as `no_seal`). A project without a history has nothing to replay.
- **MCP.** `content` and `structuredContent` are what they were; the seal is `_meta["caladrius/seal"]` and the time `_meta["caladrius/at"]`. Three answers would show hashes of their own, the entries of `history_list` and `project_save` and the digests of a `project_replay` report: the model reads them without the seals, times, versions and digests (`model_view`), and the whole answer is in `_meta["caladrius/result"]` for the program that keeps the file or checks the digests. Apothicaire's gate adds every run of digits of a tool result to the numbers it allows, which is why.
- **Replay** (`project.replay`, parameters `project` (the document) or `text`; none replays the history of the session). A scratch `Engine::new()` runs the history again in order; the project in use is not read or changed. For each step: `match`, `diverged`, `no_seal` (a project saved before seals, or a command that carries none), `not_replayable` (the parameters were too large to be kept) or `blocked` (after such a step that changed the project), with the stored and the recomputed seal; then the project the steps produce against the stored one (`state`, by the hash of their canonical text and the list of what differs). Verdicts: `verified`, `diverged`, `incomplete`, `unsealed`, `empty`. A `project.load` entry whose file is in the history is run as the project it brought; one whose content was not kept is taken as the project the earlier steps made, and the summary says so; a `project.replay` entry is not run again. A history that cannot be read is the error `history_damaged`. The report also says which engines sealed the steps and which one replayed.
- **CLI.** `project.replay --project FILE`: the file is the text to replay, nothing is loaded or written; the report is the answer, `verdict: summary` goes to standard error with the first stored and recomputed seal, and the exit code is 1 when the verdict is `diverged`. Over MCP the tool exists with the registry (`project_replay`), and the instructions of the server tell the model to report the verdict and the summary in words.
- **The application.** `File`, `Verify a project...` (and the command palette): the file is replayed on a scratch engine (`Engine::replay_bytes`, which refuses bytes that are not text like a load does); the project in the window is not read, changed or replaced, no question about unsaved changes; a page lists every step with the first 12 digits of the stored and of the recomputed seal (the whole seal on hover), the first difference marked, the engine versions, the summary sentence of the engine under the verdict, and Close; a failed verification keeps the earlier report. In the page (`apps/caladrius-web`) the same through `Pick::Verify`. Nothing numerical in `caladrius-ui`.
- **The digest** gains five replay sessions (`replay/saved`, `history-edited`, `result-edited`, `before-seals`, `params-not-kept`, one step each, one verdict each) and the 25th command example (`project.replay`): the file is made by the build that runs the digest, with the engine of the digest, and under Node the same bytes, made natively, are replayed, so a seal made on one machine that another did not reproduce would change the digest. The digest changes (`2335edbe9a69...` of T-111, now `eca8dab5dcc1...`) because the workload grew and `project.save` and `history.list` carry seals; the answers of the commands that were already in it are the same apart from the seals they carry.
- **Documents.** `docs/reproducibility.md` (plain words: guaranteed, not guaranteed, what a seal says and does not say, how to check); a pointer in the README and its sentences that become true (the toolchain sentence said "stable channel" and the file pins 1.99.1); AGENTS.md rule 10 (an answer is a function of the parameters and the project alone, and the format of the seal); `docs/validation.md`; two shots in `docs/screens/`.

## Known gaps (listed, not fixed)

- An import above 64 KiB keeps its size and an FNV-1a digest, not its text: the step cannot be run again from the file (`incomplete`), and the steps that read its worksheet are `blocked`. The `input` hash (SHA-256) of the import is in its seal, so the original file can still be checked against it. Keeping the large parameters in the file (or giving the data to the replay beside the file) is a card of its own.
- A project opened in the middle of a history whose content the history did not keep is taken as the project the earlier steps made; the summary says so and the comparison at the end still covers what follows.
- A seal is a fingerprint, not a signature: whoever can run the commands can make another file that verifies, and the time next to a seal is the clock of the machine. No claim of regulatory compliance is made anywhere.
- The replay runs on the thread of the window or of the page: a history of hundreds of fits makes the tab wait.
- A CSV with a stamp line needs `comment="#"` in the other programs that read it.
- The stored hash of an `input` is the hash of the text the program was given: for a UTF-8 file read as it is, it is what `sha256sum` prints.
- The limits of T-111 stand (the sign of a zero, `usize` on wasm32, what the workload does not reach); real cross-system proof of the seals is the CI matrix, here only Windows (dev and release) and wasm32 under Node were run.
- Apothicaire's gold values (see above).
