## Goal

The engine and command-line side of `docs/long-running-commands.md` sections 1 and 2, on top of T-143. No bridge, no Tauri, no Worker, no MCP: `caladrius-mcp` progress notifications come with `pop.fit` (T-156), when a fit lasts long enough to need them.

1. **`Engine::begin` and `Engine::finish`** (`caladrius-engine`).
   - `begin("fit.run", params) -> Result<Job, CommandError>` validates exactly as `execute` does. It takes what the fit reads from the project (the `FitInput`, with the initial estimates of FIT-INI-01 when none are given), the input hash of the seal and `engine.revision()`, and marks one job as running.
   - A `Job` is `Send`, holds no lock and no borrow of the engine, and owns a `FitRun<ModelId>`, built with `caladrius_fit::start(&input)`. That function generates the initial estimates as `run` does (T-143 revision), so the engine copies nothing from `caladrius-fit`.
   - A cancel answered after the last committed iteration gives `Cancelled`, not `Done`, even when the fit had converged and only `result::build` was left. This was found in the T-143 review. Say in the CLI sentence and in the doc comment of `finish` that a cancelled fit stores nothing, whatever its state.
   - `finish(job, outcome)` refuses with a sentence if the revision moved. Otherwise it stores the analysis, records one `fit.run` entry with its seal, clears the running job and returns the answer.
   - A cancelled job records nothing and clears the running job (`Engine::abandon(job)` or the same `finish`: the agent chooses and says why).
   - A `begin` refused for invalid parameters is recorded as a failed `fit.run`, as `execute` records it today.
2. **One running job.** While a job runs, every command with `mutates: true` (and `model.simulate` when it stores) is refused with a sentence naming the job, and nothing is recorded for it. A second `begin` is refused in the same way. Read-only commands still run.
3. **One code path.** `execute("fit.run", ..)` becomes `begin`, `run` with an observer that never cancels, then `finish`, so that there is one way a fit enters the history. The answer, the seal and the history entry of `fit.run` stay byte for byte what they are today, and so do `project.replay` and the digest.
4. **The CLI** (`apps/caladrius-cli`).
   - `fit.run --progress` prints one line per iteration on standard error (`iteration 3, wrss 12.5`, the number written as the engine writes numbers), never on standard output, so the answer and its CSV forms are unchanged.
   - `--cancel-after N` cancels after iteration N, for scripts and tests. The run then prints `fit cancelled after iteration N` on standard error, stores nothing and exits with code 1.
   - Ctrl-C cancels at the next iteration boundary in the same way, if the agent can do it with `ctrlc` (MIT or Apache-2.0). That is the only new dependency allowed, and only in `apps/caladrius-cli`. Otherwise Ctrl-C keeps its default behaviour, and the agent says so.
   - Without these flags the CLI behaves exactly as today.
5. **Tests** (`caladrius-engine` and `apps/caladrius-cli`):
   - **Same bytes.** `execute` and `begin`, a step loop, then `finish` give the same answer bytes, the same seal and the same history entry, on one fit per model family used in the engine tests: one case that converges, one that stops on the iteration limit, and one that fails.
   - **Refusals.**
     - A mutating command between `begin` and `finish` is refused and leaves the history unchanged.
     - A moved revision makes `finish` refuse.
     - A cancelled job leaves the project and the history as they were before `begin`.
   - **The CLI.**
     - `--progress` lines are strictly increasing from 1.
     - `--cancel-after 1` gives the sentence and exit code 1.
     - The output without the flags is unchanged (an existing CLI test is enough).
6. **Rules 6, 9 and 10.**
   - No `unwrap`, `expect` or `panic` on any path.
   - `cargo xtask wasm` still compiles: `Job` must not need threads.
   - `cargo xtask digest` gives the same line as on `main`.
